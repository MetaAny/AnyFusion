# 调研报告：Gateway 现状与「Web + 飞书」最简部署路径

1. **`anyfusion gateway run` 按当前代码可以启动**（`tsc --noEmit` 全库零错误，无 import 断点），**但有一个严重的行为缺口**：默认分支下它启动的是 **Pi TUI 前台进程**，**完全不启动飞书桥接**。文档（[docs/current/technical-overview.md:773](docs/current/technical-overview.md:773) 声称 "Feishu and Gateway … do not depend on which local TUI is active"）与代码不符。
2. **Gateway/飞书与新 TUI 走的是同一条 planner 路**（同一个 AnyFusion-Pi fork 二进制、同一个 v7 proposal 校验、同一个 `MetaclawSession` 收敛点），只是接入方式不同：TUI 用常驻 interactive socket 进程，gateway/飞书按 turn spawn `--mode rpc` 子进程。**不存在第二条旧 planner 路径。**
3. **仓库里没有任何"网页端"实现**：`client-ui.tsx` 是连接本地 Unix socket 的 **Ink 终端客户端**，不是浏览器界面。Web 端要落地必须新增 HTTP/WebSocket 网关（属新架构，按仓库规则需要 ADR）。
4. 完整 gateway 服务模式（socket + 飞书、无 TUI、前台常驻）**今天就能跑**，但入口是未文档化的 `METACLAW_STANDBY_TUI=1` + `anyfusion --gateway`。

---

## 一、Gateway 能否按当前代码启动？

**能启动，代码层面无断点**，但有两个逻辑坑：

### 坑 A：`gateway run` 默认不启动飞书，而是启动 Pi TUI

启动链路：`anyfusion` launcher → `exec node dist/index.js gateway run`（[anyfusion:216](anyfusion:216)）→ `parseCliArgs` 解析 `gateway run` → `cliArgs.gateway = true`（[src/cli/args.ts:30](src/cli/args.ts:30)）。

然后 `src/index.ts` 分两个分支：

| 分支 | 条件 | 行为 |
|---|---|---|
| **默认分支** | `METACLAW_STANDBY_TUI !== '1'`（[src/index.ts:158](src/index.ts:158)） | 创建 `plannerTuiSession` → 启动 gateway **socket**（[src/index.ts:173](src/index.ts:173)）→ **阻塞在 `runPlannerTuiProcess`**（[src/index.ts:192](src/index.ts:192)）→ **`cliArgs.gateway` 被完全无视，无飞书** |
| **standby 分支** | `METACLAW_STANDBY_TUI=1`（[src/index.ts:209](src/index.ts:209)） | 启动 socket server；**仅当 `cliArgs.gateway`** 才创建 gateway session + `startFeishuRuntimeBridge`（[src/index.ts:226](src/index.ts:226)、[:241](src/index.ts:241)）→ 永久阻塞（[src/index.ts:287](src/index.ts:287)） |

也就是说：**当前代码下真正的"纯网关服务"入口是 `METACLAW_STANDBY_TUI=1 anyfusion --gateway`**。全仓库只有 [src/index.ts:158](src/index.ts:158) 一处判断该变量（launcher、entrypoint.sh、Dockerfile 均未设置），且文档从未提到服务器部署需要设置它——这是 TUI 迁移到 Pi fork 后遗留的分支错位 [inferred]。

### 坑 B：默认分支的 `gateway run` 会前台拉起 Pi TUI

`runPlannerTuiProcess` spawn `anyfusion-planner`（默认 `METACLAW_PLANNER_TUI_COMMAND`，[src/tui-bridge/planner-tui-process.ts:12](src/tui-bridge/planner-tui-process.ts:12)）并 `stdio inherit` 阻塞，Pi fork 产物缺失即抛错——不符合"后台服务"语义。

### 无飞书配置时也能启动

`createFeishuBridge` 在 `!enabled || !appId` 时返回 `null`（[src/integrations/feishu-app.ts:844](src/integrations/feishu-app.ts:844)），`startFeishuRuntimeBridge` 空桥优雅返回 `null`（[src/gateway/feishu-runtime.ts:26](src/gateway/feishu-runtime.ts:26)），不会崩溃。

## 二、Gateway 与当前 TUI 是否同一条路？

**同一 planner 后端，不同接入面。** 全仓库唯一的 planner 实现就是 AnyFusion-Pi fork（`anyfusion-planner`）：

- **TUI 路径**：常驻 Pi 交互进程作为 socket 客户端连 `PlannerTuiBridge`（Unix socket `anyfusion-planner.sock`，mode 0600，`mode: interactive`）（[src/index.ts:128](src/index.ts:128)、[src/tui-bridge/planner-tui-bridge.ts:75](src/tui-bridge/planner-tui-bridge.ts:75)）
- **Gateway/飞书路径**：`MetaclawSession` 构造时创建默认 planning agent → `PlannerProcessRunner` 每 turn spawn `anyfusion-planner --mode rpc --offline ... --session <sessionId>.jsonl`（[src/planning/planner-process-runner.ts:89](src/planning/planner-process-runner.ts:89)），RPC 子进程同样通过同一 host socket 的 `proposal_submit` 回到同一 session
- 语义收敛点相同：`MetaclawSession.submitPlannerProposal` → v7 schema 校验 → `DurableKernelWorkflow` → `ControlKernel`（[src/tui-bridge/planner-tui-bridge.ts:255](src/tui-bridge/planner-tui-bridge.ts:255)）
- [CONTEXT.md:9](CONTEXT.md:9) 明确：没有 legacy intent 路由、keyword fallback 或 Codex Planner fallback

**Session 模型差异**（会影响多客户端设计）：

- **飞书 = 全局单 session**：`--gateway` 时整个飞书 bridge 共享 index.ts 创建的那一个 `MetaclawSession`（[src/index.ts:227](src/index.ts:227)），所有 chat 消息经 `session.submit(text, { awaitAsyncWork: true })` 串行化（[src/integrations/feishu-app.ts:795](src/integrations/feishu-app.ts:795)），**无 per-user 会话隔离**
- **Gateway socket = 每连接一个新 session**（`sess_gateway_<nanoid>`，断开即 shutdown）（[src/gateway/server.ts:78](src/gateway/server.ts:78)）——这正好是"每人一个会话"的现成模板
- **没有常驻 Pi 进程**：RPC 路径按 turn spawn/销毁，持久化的是 `<sessionId>.jsonl` 会话文件

## 三、"网页端"现状：目前根本不存在 HTTP Web 服务

- `MetaclawGatewayServer` 用的是 `net.createServer`（**Unix socket JSONL**，非 TCP/HTTP）（[src/gateway/server.ts:34](src/gateway/server.ts:34)），socket 文件在 `~/.local/share/anyfusion/runtime/gateway.sock`
- `anyfusion --connect` 只连**本机** socket：TTY 下用 Ink UI（`client-ui.tsx`，复用 standby TUI 的渲染工具），非 TTY 用 readline（[src/gateway/client-ui.tsx:173](src/gateway/client-ui.tsx:173)）
- 仓库唯一的 HTTP 入口只有两个：
  - **飞书 webhook**：`event_port` 默认 8787，绑所有网卡，`POST /feishu/events`（[src/integrations/feishu-app.ts:482](src/integrations/feishu-app.ts:482)、[src/utils/config.ts:49](src/utils/config.ts:49)）
  - **Markdown 预览**：`127.0.0.1:8790`（默认仅本机）（[src/utils/config.ts:35](src/utils/config.ts:35)）
- `docs/plans/` 中没有任何 Web 端计划

## 四、最简实现方案（目标：服务器上 Web + 飞书双端可用）

### 第 0 步（强烈建议，小改动）：修 `index.ts` 的分支错位

把 gateway 服务逻辑从 standby 分支里提出来，让 `anyfusion gateway run` 按文档语义工作（纯网关、前台常驻、含飞书）。约十几行改动，行为与 [docs/current/technical-overview.md:541](docs/current/technical-overview.md:541) 的文档描述对齐，**不需要 ADR**（这是修复既有文档化行为而非新架构）。

### 飞书端（改动后即用，最简）

- 服务器上 `anyfusion gateway setup` 扫码配置 → `config.yaml` 的 `gateway.platforms.feishu`（[src/gateway/setup.ts:35](src/gateway/setup.ts:35)）
- **用 `connection_mode: websocket`（默认值）**：飞书官方 SDK 长连接**出站**，**不需要公网 IP、不需要反代/内网穿透**（文档 [docs/current/technical-overview.md:239](docs/current/technical-overview.md:239) 也确认只有 webhook 模式才需要公网）
- `export FEISHU_APP_SECRET=...` + 前台 `anyfusion gateway run --project <dir>`，由服务器现有进程 supervisor 包装（[CONTEXT.md:23](CONTEXT.md:23) 已明确这是唯一合法形态）
- 访问控制：`dm_policy: pairing` + `anyfusion gateway pairing list|approve|revoke`

### Web 端（必须新增代码，需要 ADR）

现状没有任何浏览器可用的入口，三条路线：

| 方案 | 工作量 | 说明 |
|---|---|---|
| **A. 新增 HTTP+WebSocket 网关**（推荐） | 中 | 在 `MetaclawGatewayServer` 旁新增一个 HTTP/WS 端点（约 100-200 行），复用现成的 `session.submit`/`session.subscribe` 和 JSONL 协议（[src/gateway/server.ts:98](src/gateway/server.ts:98)），浏览器页面只需一个简单 HTML/JS 客户端。session 每连接一个（[src/gateway/server.ts:78](src/gateway/server.ts:78)），天然支持多人隔离 |
| B. SSH 隧道 + 本机 `--connect` | 小（零代码） | 不满足"浏览器"体验，且 Unix socket 不便 SSH 转发，不推荐 |
| C. 网页端直接走飞书网页版 | 零代码 | 若"网页端"可接受是飞书，这是最简路径 |

方案 A 属新架构决定，按 [AGENTS.md](AGENTS.md) 规则需先写 ADR。前端页面仓库里没有，可以新建或放到 AnyFusion-Pi 侧。
